# @alyt/svelte

Svelte 5 bindings for alyt: `AnalyticsProvider`, `getAnalytics`, and
`setAnalytics`.

```sh
pnpm add @alyt/core @alyt/svelte
```

In a SvelteKit root layout, create the client inside the component so each
server request gets its own instance:

```svelte
<script lang="ts">
  import { createAnalytics } from "@alyt/core";
  import { AnalyticsProvider } from "@alyt/svelte";
  import type { Snippet } from "svelte";

  let { children }: { children: Snippet } = $props();
  const client = createAnalytics();
</script>

<AnalyticsProvider {client}>
  {@render children()}
</AnalyticsProvider>
```

Read the client during a descendant component's initialization:

```svelte
<script lang="ts">
  import { getAnalytics } from "@alyt/svelte";
  import { createTracker } from "$lib/generated/tracker.js";

  const analytics = getAnalytics();
  const tracker = createTracker(analytics);
</script>

<button onclick={() => tracker.signupClicked("header")}>Sign up</button>
```

`createTracker` is generated by `@alyt/codegen` from your event schema. Its
types and `TrackOptions.only` filtering work unchanged. The returned client
is the original core client, including `track`, `identify`, `page`, `reset`,
`addPlugin`, and `removePlugin`.

## Context

Call `getAnalytics()` during component initialization, then use the returned
client in event handlers, effects, and lifecycle callbacks. It throws if no
ancestor provided a client. Nested providers override context only for their
own descendants.

You can use `setAnalytics(createAnalytics())` in a layout's instance script
instead of the provider component. `setAnalytics` returns the supplied client
and makes it available to descendants. Both helpers use Svelte's component
context; neither stores a client in module-level state.

The provider captures its initial `client`. Keep that instance for the tree's
lifetime and mutate its plugins as needed. To replace the client, remount the
tree with `{#key client}<AnalyticsProvider {client}>…</AnalyticsProvider>{/key}`.
The caller owns the client and its SDKs; unmounting the provider does not reset
or dispose of a shared client.

## Plugins and consent

Use a Svelte effect in a descendant component to scope plugin registration
to consent and component lifetime:

```svelte
<script lang="ts">
  import { googleAnalytics } from "@alyt/plugin-ga";
  import { getAnalytics } from "@alyt/svelte";

  let { consent }: { consent: boolean } = $props();
  const analytics = getAnalytics();

  $effect(() => {
    if (consent) {
      const plugin = googleAnalytics({ measurementId: "G-XXXXXXXXXX" });
      analytics.addPlugin(plugin);
      return () => analytics.removePlugin(plugin.name);
    }
  });
</script>
```

Effects run only in the browser. Initialize `gtag.js` separately under your
consent policy, or use the existing SDK initialization in your app. Each
plugin name should have one registration owner per client.

Removing a plugin stops alyt from forwarding events to it. It does not unload
the provider SDK, revoke its consent, clear cookies, or stop its automatic
collection. Apply the SDK's consent controls as well. Events without a
registered plugin are dropped; the bindings do not buffer or replay them.

The bindings do not load SDK scripts, track navigation, or implement GA4
enhanced measurement. When GA4 already collects page views, scrolls, outbound
clicks, or form events, avoid sending duplicate events through alyt. Use typed
trackers for your application's business events.

See the [runnable SvelteKit example](https://github.com/mathematic-inc/alyt/tree/main/examples/sveltekit).
